CRITICAL INVARIANTS (explicitly stated inside the scripts themselves):
  - File-First: every artifact is written to disk by the shell script
    itself (heredocs to .py/.js/.json/.css files); nothing is created
    only through `bench console` or interactive prompts.
  - No `bench console`, no raw `env/bin/python`, no `exec(open(...))`.
    `bench execute <dotted.path>` is the only sanctioned way to run
    server-side code from the shell.
  - No `drop-site`; sites are only created if missing, never dropped.
  - Idempotency: every script is designed to be safely re-run. The
    dominant pattern is "Force-Replace" (write_utf8 always overwrites
    the target file) combined with "regex-delimited hook blocks"
    (`# --- XXX_HOOKS_START ---` / `# --- XXX_HOOKS_END ---`) that are
    stripped and re-appended on every run, so re-running never
    duplicates hook content.
  - Administrator is sacred: multiple scripts (setup_realign_gate.sh
    especially) actively defend the Administrator account's roles,
    enabled flag, and session identity against being hijacked by the
    ERPNext setup wizard.
  - English identifiers, Persian labels: every DocType/Workspace/Page
    "name" is kept ASCII/English (to keep Frappe's URL routing
    deterministic: v15 builds sidebar URLs from `slug(title)` but
    resolves the route against `slug(name)` — a Persian title
    produces an unroutable slug and results in a 404 "page not found"
    error). Persian text is applied purely through the
    `translations/fa.csv` fixture mechanism (fa.csv trick — see
    Section 8 and the per-file docs of setup_phase9.sh,
    setup_phase10.sh and transport_erp.sh for the three concrete
    occurrences of this exact fix).
  - NEVER modify another app's source files from within a different
    app's setup script (explicitly asserted and even source-scanned
    for in setup_phase10.sh's verify routine).
  - NEVER send a real SMS in production code paths touched by these
    13 scripts; ir_gateway defaults to `test_mode=1` and prefixes
    outgoing text with `[TEST→original]`.

ALWAYS / NEVER summary for any future AI editing this codebase:
  ALWAYS merge `doc_events` / `fixtures` / `app_include_js` /
    `app_include_css` dictionaries and lists instead of reassigning
    them (hooks.py is a single shared Python module across the whole
    app; blind reassignment silently deletes all previously
    registered handlers — this exact danger is called out verbatim
    inside setup_phase10.5.sh's generated hooks.py comment).
  ALWAYS keep DocType/Workspace/Page `name` fields ASCII/English and
    push Persian text through `translations/<lang>.csv`.
  NEVER use `unique=1` at the database column level for
    business-identity fields (national ID, license plate); the
    project's convention is uniqueness enforced in `validate()` in
    Python, because a raw SQL unique index has caused stale-index
    problems that setup_realign_gate.sh had to repair with
    `drop_stale_unique_index()`.
  NEVER assume Number Card / Dashboard Chart Workspace widgets render
    correctly; setup_phase7.sh explicitly worked around a real
    rendering failure of these native widgets on this install by
    building a bespoke JS+API panel instead.

Routing identity rule (verified in 3 independent places — phase9,
phase10, phase12/transport_erp.sh): Frappe v15 builds the Desk
sidebar URL from `slug(title)` of a Workspace/Page but resolves the
actual route against `slug(name)`. Whenever a script's title/label
was Persian, the resulting slug (e.g. "داشبورد-مدیرعامل") could not
be resolved by the router, producing a "page not found" (404) error.
All three scripts independently converged on the SAME fix pattern:
  1. Keep `name`==`label`==`title` in pure ASCII/English for every
     Workspace and Page.
  2. Provide the Persian-facing text exclusively through
     `apps/<app>/<app>/translations/fa.csv` (format:
     `source_text,translated_text,` — 2 or 3 CSV columns), which
     Frappe's `__()` translation layer applies automatically in the
     browser without touching the underlying English identifier used
     for routing/lookup.
  3. (phase9 and phase10 additionally) actively detect and delete any
     stray Persian-named Workspace document or on-disk workspace
     folder left over from an earlier, buggy attempt, and re-run this
     cleanup on every future `bench migrate` via `after_migrate`/
     `after_install` hooks (phase10 only; phase9 relies on a one-time
     `bench execute` call inside its own shell script instead).

12. CHANGE LEDGER
====================================================================
Project convention (reverse-engineered from the 13 scripts' own
patterns, since no explicit CHANGELOG.md exists in this scope):
every change is represented as ONE new numbered/lettered phase script
that is:
  (a) additive by default (new files, new fields appended to
      field_order, new doc_events merged into the existing dict),
  (b) idempotent (safe to re-run any number of times without
      duplication or data loss),
  (c) self-verifying (a dedicated `verify_phaseN.py` module executed
      via `bench execute` immediately after the data-mutating steps),
  (d) closed with exactly one `git commit` per affected app repo
      (occasionally a `git tag`, as in setup_realign_gate.sh's
      "foundation-v1").
A REPLACE (full overwrite of an existing DocType JSON / hooks.py
block) is only used when a script is explicitly a "rewrite" of a
previous phase's own artifact (e.g., setup_phase6.sh fully replacing
setup_phase5.sh's transport_case.json) — and even then, the REPLACE
target is always something the REPLACING script's own author
originally created, never a foreign app's file.

Baseline CHANGE_ID template for any future modification to this
codebase (to be filled in by whoever performs the change):

  unless the change explicitly targets a DocType this same change

  explicit backward-compatibility note for any removed parameter>
migration: <bench migrate impact; whether a new patches.txt entry is
  required>

13. CONFLICTS & SAFETY RULES

DISCOVERED CONFLICT #1 — Two coexisting KPI/dashboard engines
  Files: setup_phase7.sh (ceo_dashboard_kpi.js +
    transport_ir.iran_transport.api.ceo_kpi.get_ceo_kpi) and
    transport_erp.sh (phase12_dashboard.js +
    transport_ir.iran_transport.phase12_workspaces.api.dashboard.
    get_dashboard/api.kpi.*)
  Nature: both independently compute overlapping metrics (open/in-
    transit/overdue counts, tonnage, profit) directly from
    `tabTransport Case` with slightly different SQL and slightly
    different overdue thresholds (phase7 has no explicit overdue
    cutoff constant visible in the KPI query itself; phase12 uses a
    hardcoded 48-hour cutoff via `_overdue_cutoff(48)`).
  ACTUAL RESOLUTION IN THIS CODEBASE: none — both engines are
    registered simultaneously (different Workspace/Page routes, so no
    JS runtime collision), meaning two independent implementations of
    similar business metrics exist side-by-side with no shared source
    of truth.
  RULE FOR FUTURE AI: do not add a third independent metrics
    implementation; if a metric must change (e.g., the overdue
    threshold), locate BOTH `_metric()`/`get_ceo_kpi()` definitions
    and change them together, or better, factor the shared logic into
    ir_base/transport_ir at a lower layer before adding any more
    dashboards.

DISCOVERED CONFLICT #2 — Redundant validate() invocation
  Files: setup_phase4.sh (Carrier/Customs Broker/Border
    Representative controllers call validate_master_mobile directly
    inside their own `validate()` method) and setup_realign_gate.sh
    (registers the SAME function again via hooks.py doc_events for
    the SAME (doctype, event) pair).
  ACTUAL RESOLUTION: harmless in practice (the function is a pure,
    idempotent normalizer/validator with no side effects beyond
    re-writing already-normalized text), but it IS a duplicate
    invocation on every single save of these 3 DocTypes.
  RULE FOR FUTURE AI: when adding a new hooks.py doc_events binding,
    first check whether the target DocType's own controller class
    ALREADY calls the same function inside its own lifecycle method
    before also registering it via hooks.py — prefer ONE registration
    site per (doctype, event, function) triple.

DISCOVERED CONFLICT #3 — Fixture file path collision risk
  Files: setup_phase7.sh, setup_phase84.sh, and setup_realign_gate.sh
    ALL write to the exact same physical path:
    `apps/transport_ir/transport_ir/fixtures/translation.json`.
  Nature: setup_phase7.sh and setup_phase84.sh both use a Python
    dict-merge-then-dump pattern (load existing rows, merge by
    (language,source_text) key, dump full set) — genuinely additive
    and order-independent between these two. setup_realign_gate.sh,
    however, writes this file with a PLAIN heredoc FULL OVERWRITE
    (no load-existing-then-merge step), containing only its own 18
    translation rows.
  ACTUAL RESOLUTION IN THIS CODEBASE: none via code — safety is
    achieved ENTIRELY through EXECUTION ORDER (setup_realign_gate.sh
    is documented to run BEFORE phase5/6/7/8 in Section 2.3, so its
    overwrite happens before phase7/phase84 ever add their own rows,
    and phase7/phase84's own merge logic correctly preserves
    realign_gate's 18 rows when they run afterward).
  RULE FOR FUTURE AI: NEVER re-order setup_realign_gate.sh to run
    after setup_phase7.sh or setup_phase84.sh; if a change requires
    running realign_gate later in a pipeline, its translation.json
    write MUST be converted to the same load-merge-dump pattern
    phase7/phase84 already use, or Persian labels seeded by those two
    phases will silently disappear from the Desk sidebar (a 404-
    adjacent regression, not a hard crash, making it easy to miss in
    testing).

DISCOVERED CONFLICT #4 — hooks.py doc_events supersession for
  Driver/Vehicle
  Files: setup_phase4.sh registers Driver.validate/Vehicle.validate
    inside a `PHASE4_HOOKS_START/END` marker block; setup_realign_
    gate.sh explicitly regex-deletes BOTH its own prior
    `REALIGN_GATE_HOOKS_START/END` block AND the `PHASE4_HOOKS_START/
    END` block, then writes a single new combined block containing
    equivalent bindings for Driver/Vehicle plus 3 additional bindings
    (Carrier/Customs Broker/Border Representative).
  ACTUAL RESOLUTION: functionally safe (the replacement targets are
    identical dotted paths), but structurally this means phase4's OWN
    hooks.py contribution has a finite lifespan — it is guaranteed to
    be deleted the moment setup_realign_gate.sh runs.
  RULE FOR FUTURE AI: never assume a `# --- PHASEN_HOOKS_START/END
    ---` marker block is permanent; before hand-editing hooks.py,
    grep for ALL marker blocks currently present and identify which
    script "owns" (last wrote) each one, because a later phase may be
    designed to delete an earlier phase's marker block entirely as
    part of a deliberate consolidation (as realign_gate does to
    phase4).

GLOBAL SAFETY RULES DERIVED FROM ALL 13 FILES (for any AI editing
this codebase going forward):
  1. Treat `hooks.py`, every `fixtures/*.json`, and every
     `translations/*.csv` file as SHARED MUTABLE STATE across scripts
     — always read-merge-write, never blind-overwrite, UNLESS you are
     also updating every other script that shares the same file to
     match the new merge contract (as documented in Conflict #3).
  2. Never set a non-default `workflow_state` directly on `insert()`
     in Frappe v15; always insert with the DocType's default state
     and perform the state jump via `frappe.db.set_value(...,
     update_modified=False)` immediately afterward (the "Bridge
     Pattern", first discovered as a bug and fixed in setup_phase6.sh,
     reused unchanged in setup_phase10.5.sh's verify-adjacent test
     code).
  3. Never assume `frappe.db.exists()` returns a boolean; it returns
     the matched document NAME (or None) — use `frappe.db.count()`
     with an equality filter when a strict boolean/integer 0-or-1
     check is required (documented as a "CRITICAL FIX" discovered in
     setup_phase5.sh's Preflight).
  4. Never persist raw secrets (passwords, API keys) inside any
     fixture/JSON/heredoc file that will be committed to git;
     setup_realign_gate.sh's `secrets.env`/`.gitignore` pattern is the
     project's sanctioned mechanism.
  5. Keep every new DocType/Workspace/Page `name` ASCII/English;
     route all Persian labeling through translation fixtures.
  6. Keep the SMS/Integration Kill-Switch pattern (`enabled`/
     `integration_enabled` flags checked FIRST, before any adapter
     resolution) for any future outward-facing integration; never
     wire a new external side effect (SMS, webhook, ERP push) without
     an equivalent boolean gate defaulting to OFF.
